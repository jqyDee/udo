================================================================================
                    UDO: THE ACADEMIC WORKSPACE & CLI ROADMAP
================================================================================

PROJECT OVERVIEW:
A high-performance, asynchronous Rust CLI and TUI tool designed for university 
students to manage coursework, automate local file/folder generation, track time 
spent per assignment using adaptive strategies (Tmux & File Watchers), and 
provide deep productivity insights.

STATUS LEGEND:  [x] done   [~] partly done / done differently   [ ] open
"Status:" lines describe the actual code (last checked 2026-09-25).

DONE OUTSIDE THE ORIGINAL PLAN:
    [x] Recursive node tree (`src/model/`): Root -> Workspace -> Project ->
        Task, one `.udo.toml` per container, atomic + fsynced writes.
    [x] Tree operations: load, save, create, update, delete (unregister only,
        never deletes folders), name lookup (`resolve`).
    [x] Safety: unloadable child folders stay registered, never overwrite an
        existing `.udo.toml`, load errors name the broken file.
    [x] `udo list`, tree navigation, collapse/expand with saved view state
        (`view.toml`, kept separate from the data files).
    [x] `UDO_ROOT` override + `scripts/seed-testdata.sh` for throwaway data.
    [x] Architecture docs: `docs/tree/*.puml`.

Goal: Build robust CLI commands to manipulate local folders and TOML metadata.

[x] 2.1 The `Add` Command

    * Setup a local template directory (`~/.config/udo/templates/`).
    * Auto-copy standard file structures (e.g., `main.typ`, configuration files)

[ ] 2.3 Pluggable Storage Backends  (added 2026-09-25)
    Goal: Swap where task data is stored (per-folder `.udo.toml` files, one
    combined file, or a database) without touching CLI/TUI code.
    Note: only *storage* is swappable. Real workspace/project/task folders stay
    on disk with every backend (work happens there, scripts run there).
    Rule until then: nothing outside `Tree` touches storage.

    [ ] 2.3.1 `Store` abstraction + `FileStore` (pure refactor, ~half a day)
        * Define `Store`: `load() -> Node`, `save_container(&Container)`,
          `load_view()`, `save_view(&ViewState)`.
        * `Tree` holds a `Backend` enum (`Files(FileStore) | Sqlite(..) | ..`)
          that forwards calls. Enum over `dyn`: async fns in traits are not
          dyn-compatible without boxing, and the backends are known.
        * Move current code into `FileStore`: `ContainerData` load/save,
          `build_container`, `unloaded` handling, "dir already has .udo.toml"
          check, view.toml.
        * Add a `Tree` constructor; tests stop building `Tree { .. }` directly.
        * Done when all existing tests pass unchanged in behaviour.

    [ ] 2.3.2 Stable IDs
        * Give `Task` a `uuid`: tasks are currently keyed by name among
          siblings, so a rename breaks any DB key.
        * Containers keep `dir` as ID (unique thanks to the overwrite check).
        * Bonus: view.toml can then remember the selected node.

    [ ] 2.3.3 `SingleFileStore` (~1-2 hours)
        * Whole tree in one TOML/JSON file. Cheapest proof that the
          abstraction holds, and already gives "one combined file".

    [ ] 2.3.4 `SqliteStore` (~1 day)
        * One `udo.db`; `rusqlite` inside `spawn_blocking`, or `sqlx`.
        * Tables: `containers(dir PK, parent, name, kind, settings)`,
          `tasks(id PK, container, name, dir, status, due)`.
        * `save_container` = one transaction (upsert container, replace tasks).
        * Gains: transactions (CLI + TUI no longer overwrite each other),
          cross-workspace queries (e.g. "due this week").
        * Loses: human-readable, git-friendly `.udo.toml` per folder.

    [ ] 2.3.5 Backend selection & migration (~few hours)
        * Choose backend via env var (`UDO_STORE`), a small config in the root
          dir, or by detecting `udo.db`.
        * `udo export` / `udo import`: load with one store, save all with another.

PHASE 4: SPECIALIZED TIME-TRACKING PLUGINS
--------------------------------------------------------------------------------
Goal: Build contextual work trackers matching specific software workflows.

[ ] 4.1 The Tmux/Neovim Strategy ("Process Existence" Tracker)
    * Spawn detached tmux sessions (`tmux new-session -d`) bound to task folders.
    * Implement smart client switching (detecting if already inside tmux via `$TMUX`).
    * Spawn a background tokio task (`tokio::spawn`) to poll session status via 
      `tmux has-session` without blocking the main thread.
    * Automatically calculate elapsed seconds on session death and update `course.toml`.

[ ] 4.2 The File Watcher Strategy ("Activity Polling" Tracker)
    * Implement the `notify` crate to watch target directories for file modifications.
    * Track file-save events as active work increments.
    * Implement an idle timeout mechanism to automatically pause tracking after 
      prolonged inactivity.
